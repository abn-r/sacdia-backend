# Resend Email Setup Runbook

## Overview

SACDIA uses [Resend](https://resend.com) for transactional email. Three subdomains are verified — one per Render service environment — so each service has a distinct, trackable sender identity.

| Environment | Sender address                  | Render service        |
|-------------|----------------------------------|-----------------------|
| development | noreply@dev.sacdia.app          | sacdia-backend-dev    |
| staging     | noreply@staging.sacdia.app      | sacdia-backend-staging|
| production  | noreply@sacdia.app              | sacdia-backend-prod   |

Free tier limits: 3 000 emails/month, 100 emails/day. The BullMQ queue limiter is set at 90/day to leave 10 headroom for manual dashboard sends.

---

## Step 1 — Create Resend account and API keys

1. Sign up at https://resend.com
2. Navigate to **API Keys** and create one key per environment:
   - `sacdia-dev` (restricted to `dev.sacdia.app` domain)
   - `sacdia-staging` (restricted to `staging.sacdia.app`)
   - `sacdia-prod` (restricted to `sacdia.app`)
3. Copy each key — it is shown only once.

---

## Step 2 — Add and verify domains in Resend

Add each subdomain separately in **Resend > Domains**:

- `dev.sacdia.app`
- `staging.sacdia.app`
- `sacdia.app`

For each domain, Resend will provide a set of DNS records to add. Add them in the Cloudflare zone for `sacdia.app`.

### DNS records per subdomain

The exact CNAME values are generated by Resend; the pattern is shown below. Replace `<resend-value>` with the actual values from the Resend dashboard.

#### dev.sacdia.app

```
# SPF — TXT record on dev.sacdia.app
dev.sacdia.app  TXT  "v=spf1 include:amazonses.com ~all"

# DKIM — 3 CNAME records
resend._domainkey.dev.sacdia.app  CNAME  <resend-dkim-1>.dkim.resend.com
resend2._domainkey.dev.sacdia.app CNAME  <resend-dkim-2>.dkim.resend.com
resend3._domainkey.dev.sacdia.app CNAME  <resend-dkim-3>.dkim.resend.com

# DMARC — TXT record on _dmarc.dev.sacdia.app
_dmarc.dev.sacdia.app  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@sacdia.app"
```

#### staging.sacdia.app

```
staging.sacdia.app  TXT  "v=spf1 include:amazonses.com ~all"

resend._domainkey.staging.sacdia.app  CNAME  <resend-dkim-1>.dkim.resend.com
resend2._domainkey.staging.sacdia.app CNAME  <resend-dkim-2>.dkim.resend.com
resend3._domainkey.staging.sacdia.app CNAME  <resend-dkim-3>.dkim.resend.com

_dmarc.staging.sacdia.app  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@sacdia.app"
```

#### sacdia.app (production)

```
sacdia.app  TXT  "v=spf1 include:amazonses.com ~all"

resend._domainkey.sacdia.app  CNAME  <resend-dkim-1>.dkim.resend.com
resend2._domainkey.sacdia.app CNAME  <resend-dkim-2>.dkim.resend.com
resend3._domainkey.sacdia.app CNAME  <resend-dkim-3>.dkim.resend.com

_dmarc.sacdia.app  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@sacdia.app"
```

> Cloudflare propagates DNS within seconds for zones it manages, but Resend's verification check can take up to 30 minutes. Click "Verify" in the Resend dashboard after adding records.

## Step 3 — Set environment variables in Render

For each Render service, go to **Environment > Environment Variables** and add:

### sacdia-backend-dev

```
EMAIL_ENABLED=false
RESEND_API_KEY=re_dev_xxx
RESEND_FROM_EMAIL=SACDIA Dev <noreply@dev.sacdia.app>
RESEND_REPLY_TO=hola@sacdia.app
```

Keep `EMAIL_ENABLED=false` until DNS is verified for `dev.sacdia.app`.

### sacdia-backend-staging

```
EMAIL_ENABLED=true
RESEND_API_KEY=re_staging_xxx
RESEND_FROM_EMAIL=SACDIA Staging <noreply@staging.sacdia.app>
RESEND_REPLY_TO=hola@sacdia.app
```

### sacdia-backend-prod (production)

```
EMAIL_ENABLED=true
RESEND_API_KEY=re_prod_xxx
RESEND_FROM_EMAIL=SACDIA <noreply@sacdia.app>
RESEND_REPLY_TO=hola@sacdia.app
```

## Step 4 — Verify in Resend dashboard

After setting `EMAIL_ENABLED=true` and deploying:

1. Trigger a test flow: register a new user in the mobile app to fire `email-verification`.
2. In the Resend dashboard, go to **Logs** and confirm:
   - Status: `delivered` (not `bounced` or `failed`)
   - Sender: matches the expected FROM address
   - DKIM/SPF: both passing (shown in email headers)
3. Check the inbox of the test account — the email should arrive within seconds.

## Troubleshooting

### Email not arriving

1. Check Resend **Logs** — if status is `failed`, the error message is shown.
2. Confirm `EMAIL_ENABLED=true` is set in the Render service environment.
3. Verify the domain is in `Verified` state in Resend **Domains**.
4. Check BullMQ job status via Redis (`bull:emails:failed` key) — failed jobs are kept for audit (`removeOnFail: false`).

### Bounce or spam

1. Confirm all three DKIM CNAME records are present in Cloudflare.
2. Confirm the SPF TXT record is present (`v=spf1 include:amazonses.com ~all`).
3. Confirm DMARC record exists and is syntactically valid — use https://mxtoolbox.com/dmarc.aspx.
4. Resend emails are relayed via Amazon SES; if a recipient's provider blocks SES, there is no workaround beyond allowlisting.

### Rate limit hit (90/day BullMQ limiter)

The queue limiter pauses jobs automatically without consuming retry attempts. Jobs will resume the next day. If legitimate volume requires raising the limit, upgrade to Resend Pro and adjust `limiter.max` in `src/common/email/email.module.ts`.

### `RESEND_API_KEY` not set

`ResendEmailProvider` initializes the Resend client with an empty string when the key is absent. Calls will return a 401 error from Resend. BullMQ will retry up to 5 times with exponential backoff before marking the job as failed.

## Architecture reference

```
EmailService (facade)
  └── EmailQueueProducer      BullMQ producer; enqueues to 'emails' queue
        └── EmailProcessor    @Processor('emails') worker
              ├── render()    @react-email/render → HTML + plain text
              └── ResendEmailProvider.send()  → Resend API
```

Templates are in `src/common/email/templates/`. All templates use the shared `_layout.tsx` for consistent branding and GDPR-compliant footer.

Consumers that trigger emails:
- `auth.service.ts` — `sendEmailVerification` (after registration / resend-verification)
- `better-auth.service.ts` — `sendPasswordReset` (after token generation)
- `account-deletion.service.ts` — `sendAccountDeletionConfirmed` (post-commit fire-and-forget)
- `data-export.processor.ts` — `sendDataExportReady` (after GDPR export file upload)
